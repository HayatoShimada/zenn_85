古着屋のオンラインストア（Shopify）に、**ことばの意味や写真で商品を探せる検索窓**を付けました。「冬に着る暖かいアウター」「キャンプに行く服」と書けば、品名に「アウター」「キャンプ」が入っていなくても、フリースやマウンテンパーカーが並びます。カメラのボタンで服の写真を撮れば、似た商品を探します。

![写真で探した結果。フリースの写真から、似たフリースが並んでいる](/images/clef-product-search/photo-search.png)

結論から言うと、使っているのは埋め込みベクトルではなく、Cloudflare Workers AI の **Clef-flash**（`@cf/cloudflare/clef-flash`）という「はい・いいえの確率を返す」判定モデルです。在庫の全商品（約300点）について、毎回「この商品は検索の意図に合うか」を聞いて、確率の高い順に並べています。

- 検索1回で約6万トークン。料金は**1回約0.4円**（キャッシュに当たれば0円）
- Workers AI の無料枠（1日1万ニューロン）で、1日に約45回の検索がまかなえる
- かかる時間は、ことばで約3秒、写真で約4秒
- 費用も時間も商品の数に比例するので、数百点の店に向いた作り方です

## なぜ埋め込みではなく、判定モデルなのか

意味で探す検索といえば、商品と検索語を埋め込みベクトルにして、近いものを探すのが定番です。ただ、古着屋の商品だと、うまくいかないところがありました。

- 品名が「Heavy Flannel Check Shirts L/S」のような英語の決まった形で、「秋」「キャンプ」「暖かい」といった、お客さまが検索に使うことばが入っていない
- 「冬に着る暖かいアウター」で探したいのは「アウターという単語に近い商品」ではなく、「冬に着られて暖かい上着」です。この条件の組み合わせが、ベクトルの近さに出にくい
- しきい値を決めにくい。コサイン類似度が 0.78 なら合うのかどうか、検索語ごとに感覚が変わる

Clef は、質問に対して「はい」の確率（`noul`）をそのまま返します。「この商品はお客さまの検索の意図に合うか」と聞けば、0.97 のように答えが返ってきます。しきい値は「確率 0.5 以上を出す」のように決められて、店の人にも説明しやすくなります。

Clef-flash は前に、商品写真の分類で使っていました（[Clef-flashでの画像分類をベンチマークする](https://zenn.dev/85store/articles/jev_benchmark_test_onpre_cloud)）。その感触がよかったので、検索にも使ってみました。

ちなみに、検索窓の見出しは「Vector Search」です。中身はベクトルではないのですが、お客さまに「AI で意味から探せる」ことが伝わる名前にしました。

## 構成

```
[お客さま（shop.85-store.com）]
   │ ことば: GET /v1/search?q=…
   │ 写真:   POST /v1/image-search（長い辺 768px の JPEG）
   ▼
[Cloudflare Worker（search.85-store.com）]
   ├─ 在庫の商品: Shopify Storefront API（5分キャッシュ）
   ├─ 商品の属性: KV（色・柄・季節・厚さ…。手元の GPU で前もって判定しておく）
   ├─ 判定: Workers AI の Clef-flash（30点ずつ並列に聞く）
   ├─ 結果: Cache API（同じ検索語・写真は1時間）
   └─ 検索された言葉: D1（店の CMS で見る）
   │ { results: [{ handle, score }] }
   ▼
[Shopify テーマ] ハンドルの順に、テーマの商品カードで並べる
```

Worker が返すのは商品のハンドルと確率だけです。商品カード（写真・名前・価格）は、テーマがいつもの部品で描きます。

## 商品を1行の説明にする

Clef には、商品ごとに1つ質問を作って渡します。質問の中に、商品を1行で説明した文を入れます。

```ts
// 商品を1行で表す（Clef の質問に入れる）
export function describe(p: Product): string {
  const facts = [p.productType, p.brand, p.material, p.attributes].filter(Boolean).join(" / ");
  const description = p.description.replace(/\s+/g, " ").trim().slice(0, 80);
  return `${p.title}（${facts}）${description}`;
}
```

品名と説明だけでは、「暖かい」「秋冬」のような情報が足りません。そこで、商品の写真と説明から**種類・色・柄・テイスト・季節・厚さ・シルエット・系統**を前もって判定し、KV に入れています。

この判定も Clef で行っています。ただし、手元の GPU（Radeon RX 7900 XTX）で動かしているので、クラウドの費用はかかりません。新しい商品を入れたときに、まだ判定していない商品だけを判定して、KV に上げ直します。

属性が無い商品も、品名・種類・説明だけで検索の対象になります。

## Clef に「合うか」を聞く

検索語は `state` に入れ、商品ごとに `noul`（はい・いいえ）の質問を作ります。商品が多いと入力が長くなりすぎるので、30点ずつに分けて並列に聞きます。

```ts
export function buildRequest(input: SearchInput, products: Product[], askMeaningful = false): ClefRequest {
  const text = "image" in input ? IMAGE : TEXT;
  const questions: ClefRequest["questions"] = {};
  if (askMeaningful) questions.meaningful = { type: "noul", instructions: text.meaningful };
  products.forEach((p, i) => {
    questions[`p${i}`] = { type: "noul", instructions: `${text.product}: ${describe(p)}` };
  });
  if ("image" in input) {
    return { model: "clef-flash", state: { task: text.task }, questions, images: [input.image] };
  }
  return { model: "clef-flash", state: { task: text.task, query: input.query }, questions };
}

// 全商品の確率を出し、高い順に並べる
export async function rank(input: SearchInput, products: Product[], ask: Ask) {
  const groups = chunks(products, 30);
  const answers = await Promise.all(groups.map((g, i) => ask(buildRequest(input, g, i === 0))));
  // …answers[i][`p${j}`].noul を集めて、高い順に並べる
}
```

質問の文は次のとおりです。

| | ことばで探す | 写真で探す |
|---|---|---|
| task | 古着・セレクトショップのオンラインストアで、お客さまの検索語に合う商品を選ぶ | 古着・セレクトショップのオンラインストアで、お客さまが撮った写真の服や小物に似た商品を選ぶ |
| 商品ごと | この商品はお客さまの検索の意図に合うか: （商品の1行） | この商品は、写真に写っている服や小物と、種類・色・柄・雰囲気が似ているか: （商品の1行） |

Worker は確率 0.3 以上の商品を、高い順に最大48点返します。どこまで出すかは、テーマの設定（既定は 0.5 以上）で決めます。

### でたらめな検索語をはじく

作ってみて困ったのが、キーボードを適当に打ったような**でたらめな文字列でも、商品の確率が 0.8 を超えることがある**ことでした。検索語に意味が無いと、モデルが「合わないとも言えない」と判断するようです。

そこで、最初のグループのリクエストにだけ、「検索語は、商品を探す意味のあることばか」という質問を1つ足しました。この確率が 0.2 未満なら、何も返しません。

| 検索語 | 意味のあることばか |
|---|---|
| 冬に着る暖かいアウター | 0.95 |
| Lee（ブランド名） | 0.3 前後 |
| 今日の天気 | 0.04 |

ブランド名やサイズ（XL）だけの検索ははじかないように、質問の文に「ブランド名（英字）やサイズだけでも yes」と書いています。写真のときは、同じ位置で「写真に、服・靴・帽子・バッグ・小物など、身につけるものが写っているか」を聞きます。風景の写真なら 0.02 前後になります。

## 写真で探す

テーマのカメラのボタンから写真を選ぶ（撮る）と、ブラウザで長い辺 768px の JPEG に縮めてから送ります。iPhone の写真をそのまま読み込むと重いので、`createImageBitmap` に縮める大きさを渡して、読み込みと縮小を一度に済ませています。

```js
const bitmap = await createImageBitmap(file, {
  resizeWidth: 768,
  resizeQuality: 'high',
  imageOrientation: 'from-image', // 撮ったときの向きに合わせる
});
```

Worker は写真を base64 にして、30点ずつの各リクエストに `images` として付けます。写真は30点ごとに1回ずつ送るので、ことばで探すときより1割ほどトークンが増えます。

## キャッシュとレート制限

- 同じ検索語の結果は、Cache API に1時間置きます。キャッシュのキーは、そろえた検索語（NFKC にして小文字にしたもの）です。写真は SHA-256 で見分けます
- 商品が売れたり属性が変わったりしたら、そのキャッシュは使いません。キーに、商品と属性のハッシュを入れています
- 1つの IP から1分に20回まで（Workers の Rate Limiting）。キャッシュに当たった検索は数えません

検索窓の下に並べた「検索の例」はみんなが押すので、ほとんどがキャッシュに当たります。

## テーマ側：商品カードは Section Rendering API で描く

Shopify のテーマ（Horizon）には、AI 検索のセクションを1つ足しました。Worker から返ってきたハンドルを、次の URL で読み込みます。

```
/search?q=ai-handles:<ハンドル,...>&section_id=<検索ページのこのセクション>
```

セクションの Liquid は、検索語が `ai-handles:` で始まっていたら、そのハンドルの商品を `all_products` から取り出して、テーマの商品カードで描いて返します。カードの見た目をテーマとそろえられて、価格や在庫の表示も Shopify に任せられます。

検索ページでは、ページを開いたときに検索語で AI 検索をします。AI がえらんだ商品の下に、いつものキーワード検索の結果も並びます。ヘッダーの検索から来ても、AI で探します。

## 検索の例は季節で切りかえる

![検索窓と、検索の例](/images/clef-product-search/search-box.png)

検索窓の下には、押すとそのことばで探せる例を出しています。在庫の傾向（ネルシャツ、フリース、スウェット、ウールのニット、アロハシャツが多い）から、季節ごとに14語ずつ作りました。そのうち4つを、来るたびにランダムに選んで出します。

例の言葉は、どれも本番の AI 検索で試しています。合う在庫が1点しか無かった「デニムジャケット」や、関係の薄い商品が上位に出た「クリスマスのプレゼント」は外しました。

## 検索された言葉を、店の CMS で見る

お客さまが検索した言葉は、D1 に日ごとに記録しています。IP などは残さず、検索語・回数・出した商品の数だけです。写真の検索は、回数だけを数えます。

店の CMS（Payload CMS）に「検索された言葉」の画面を作り、Bearer トークンで Worker から集計を読んでいます。**AI が1点も選べなかった言葉**だけを絞り込めるので、「お客さまが探しているのに、店に無いもの」が分かります。

## コスト

Workers AI の料金は、使ったニューロンで決まります。Cloudflare の料金表では、Clef-flash は入力100万トークンあたり 3,455 ニューロン（$0.038）、出力は無料です。1,000 ニューロンあたり $0.011 で、1日 10,000 ニューロンまでは無料です。

Cloudflare の GraphQL Analytics（`aiInferenceAdaptiveGroups`）で、実際に使った量を見ました。商品が約300点のときの値です。

| | リクエスト数 | 入力トークン | ニューロン | 料金（1ドル150円） |
|---|---|---|---|---|
| ことばで探す1回 | 11（30点ずつ） | 約5.5〜6.5万 | 約190〜230 | 約0.3〜0.4円 |
| 写真で探す1回 | 10〜11 | 約6.5〜7.5万 | 約230〜255 | 約0.4円 |

無料枠の1日1万ニューロンで、キャッシュに当たらない検索が1日に約45回まかなえます。それを超えた分の料金は、次のくらいです。

| キャッシュに当たらない検索 | 1日のニューロン | 1か月の料金 |
|---|---|---|
| 1日 45回まで | 〜1万 | 0円 |
| 1日 100回 | 約2.2万 | 約600円 |
| 1日 300回 | 約6.6万 | 約2,800円 |

参考までに、検索の例を決めるために約70語を続けて試した日は、1日で 18,040 ニューロン（無料枠を超えた分が約13円）でした。開発やテストで何十回と検索しても、費用は気にならない程度です。

ほかに使っている Workers・KV・D1・Cache API は、この量なら無料枠の範囲に収まっています。商品の属性の判定は手元の GPU で動かしているので、電気代だけです。

### 費用は商品の数に比例する

この作り方の弱いところは、**検索のたびに全商品を判定する**ことです。費用も時間も、商品の数に比例して増えます。

- 300点なら、1回約0.4円・約3秒
- 3,000点なら、1回約4円になり、リクエストも100本ほどに増える

古着屋は1点ものが多く、在庫は数百点で落ち着くので、今はこのままで十分です。商品が数千点を超える店なら、先に埋め込みベクトルで候補を100点ほどに絞り、そこだけ Clef に聞く（並べ直しに使う）のがよさそうです。

## まとめ

- 判定モデルの Clef-flash に「この商品は検索の意図に合うか」を商品ごとに聞くだけで、ことばと写真の両方で意味から探せる検索ができた
- 確率がそのまま返るので、しきい値を決めやすい。でたらめな検索語は「意味のあることばか」という質問を1つ足してはじく
- 品名に無い情報（季節・厚さ・雰囲気）は、前もって写真から属性を判定して補う
- 検索1回約0.4円。数百点の店なら、無料枠と1か月数百円で動く

実装は、ほぼ Claude Code と一緒に書きました。テーマのセクション、Worker、CMS の画面をまたいだ変更も、一続きの作業で進められました。
